day32 商户查询缓存、缓存一致性与缓存穿透雪崩

一、缓存概述

1.1 什么是缓存

缓存（Cache）是数据交换的缓冲区，数据一般从数据库中获取，存储在内存中。内存的读写性能远高于磁盘，缓存可以防止过高的数据访问量直接冲击数据库，导致系统瘫痪。

1.2 缓存的作用与成本

作用：降低数据库读写压力，提高系统响应速度。

成本：

成本维度 说明
数据一致性 缓存数据来源于数据库，数据库变化时缓存若未同步，会出现一致性问题
代码维护 增加缓存逻辑后，代码复杂度上升
运维 需要维护 Redis 等缓存基础设施

三、缓存更新策略

3.1 三种缓存更新策略

策略 说明 一致性 维护成本
内存淘汰 Redis 内存达到 maxmemory 时自动淘汰数据 弱 最低
超时剔除 为 key 设置 TTL，到期后 Redis 自动删除 一般 低
主动更新 编码手动删除或更新缓存 强 高

根据对一致性的要求选择策略，也可以多种结合使用。项目中采用了超时剔除 + 主动更新结合的方式。

3.2 主动更新方案选择

三种主动更新方案：

方案 说明
Cache Aside Pattern 人工编码，调用者在更新数据库后更新缓存（双写方案）
Read/Write Through Pattern 由系统本身处理数据库与缓存的一致性
Write Behind Caching Pattern 调用者只操作缓存，其他线程异步处理数据库

三种方案中，Cache Aside Pattern（开发者编码）最优，可控性最强。

3.3 删除缓存还是更新缓存

在 Cache Aside 方案下，操作数据库后对缓存进行更新还是删除？

操作 问题
更新缓存 频繁更新数据库时，每次都要更新缓存；若期间无查询，中间的更新操作没有意义
删除缓存 频繁更新数据库时，若期间无查询，只需操作数据库，缓存等下次查询时再加载

删除缓存更优：避免无效写操作，查询时再按需加载。

3.4 先删缓存还是先更新数据库

这个问题涉及线程安全，需要分析并发场景下的不一致风险。

方案一：先删缓存，再更新数据库

  1. 线程 1 删除缓存
  2. 线程切换给线程 2（查询操作）
  3. 线程 2 缓存未命中，查询数据库得到旧数据
  4. 线程 2 将旧数据写入缓存
  5. 线程 1 更新数据库
  6. 结果：缓存中是旧数据，数据库是新数据，不一致

方案二：先更新数据库，再删除缓存

  1. 线程 2 查询缓存未命中，从数据库查询到旧数据
  2. 线程切换给线程 1（更新操作）
  3. 线程 1 更新数据库，删除缓存
  4. 线程切换回线程 2，将旧数据写入缓存
  5. 结果：缓存中是旧数据，不一致

结论：先更新数据库，再删除缓存更优。

原因分析：

  • 先删缓存：线程切换发生在一个长时间段（查询数据库、处理数据的过程中）

  • 先更新数据库：线程切换发生在一个极短时间（查到数据库旧数据与写入缓存之间的间隔）

  • 此外，先更新数据库方案发生不一致还需要恰好在一个查询任务执行时进入更新操作，概率较小

四、缓存穿透

4.1 什么是缓存穿透

缓存穿透是指客户端请求的数据在缓存和数据库中都不存在，缓存永远不会生效，这些请求会直接到达数据库。如果大量这样的请求同时到来，会给数据库带来巨大压力。

4.2 解决方案

方案 优点 缺点
缓存空对象 实现简单，维护方便 占用额外内存，可能造成短期数据不一致
布隆过滤 内存占用少，没有多余 key 实现复杂，存在误判风险（哈希冲突）

项目中采用缓存空对象方案。

4.3 缓存空对象实现

在 queryWithPassThrough 方法中（见 2.2 节），缓存空值的核心逻辑：

  1. 查询缓存命中且不为 null 且不为空字符串 → 返回数据
  2. 查询缓存命中但不为 null 且为空字符串 → 说明之前查过数据库未查到，直接返回 null，不再查询数据库
  3. 缓存未命中 → 查询数据库
  4. 数据库未查到 → 将空字符串 "" 写入缓存，TTL 为 2 分钟（CACHE_NULL_TTL）
  5. 数据库查到 → 正常建立缓存并返回

StrUtil.isNotBlank(shopJson) 用于区分正常数据和空值缓存：空字符串 "" 不会被 isNotBlank 判定为存在，但也不为 null，因此通过 shopJson != null 可以识别出这是之前缓存的空值。

五、缓存雪崩

5.1 什么是缓存雪崩

缓存雪崩是指在同一时段大量的缓存 key 同时失效或者 Redis 服务器异常，导致大量请求到达数据库，带来巨大压力。

5.2 解决思路

方案 说明
TTL 设置随机数 给不同 key 的 TTL 添加随机值，避免同时失效
Redis 集群 提高服务的可用性，防止单点故障
降级限流 给缓存业务添加降级限流策略
多级缓存 构建多级缓存体系
