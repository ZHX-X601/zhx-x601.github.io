1.2 短信登录的整体流程

短信登录分为三步：

  1. 发送短信验证码：用户提交手机号，后台校验格式后生成 6 位验证码，存入 Session。
  2. 验证码登录：用户提交手机号和验证码，后台从 Session 取出验证码比对，一致则根据手机号查询用户，不存在则自动创建，最后将用户信息存入 Session。
  3. 校验登录状态：后续请求携带 Cookie 中的 JSESSIONID，后台通过拦截器从 Session 取出用户信息，未登录则拦截。

二、基于 Session 实现短信登录

2.1 对 Session 的理解

每个 Tomcat 服务器维护一个 Session 池。当浏览器发起请求并调用 session.setAttribute(key, value) 时：

  1. 服务器为该浏览器生成一个 SessionID；
  2. 创建一个 Session 对象，将字段名与字段值存入其中；
  3. 将 SessionID 通过 Cookie 返回给浏览器；
  4. 下次请求时浏览器携带该 SessionID，服务器据此找到对应的 Session 对象。

Session 的核心作用是在无状态的 HTTP 协议下保存用户的登录状态。

3.2 ThreadLocal 保存用户信息

UserHolder 封装了基于 ThreadLocal 的用户存取：

为什么用 ThreadLocal：Tomcat 从线程池中取一个线程处理每个请求，请求结束后线程归还线程池。ThreadLocal 以当前线程为 key 存储数据，保证每个线程只能访问自己的那份用户信息，实现线程隔离。Controller 中通过 UserHolder.getUser() 获取当前登录用户。

注意：必须在 afterCompletion 中调用 removeUser() 清除 ThreadLocal，否则线程复用会导致数据错乱和内存泄漏。

4.1 为什么用 UserDTO

User 实体包含 password 等敏感字段，直接存入 Session 并返回前端存在安全风险。UserDTO 只保留必要字段：

使用 UserDTO 的好处：

五、Session 共享问题

5.1 问题描述

在集群部署时，每台 Tomcat 服务器的 Session 是独立的：

用户第一次请求落到 Tomcat1 并在其 Session 中保存了登录信息，第二次请求可能被负载均衡分发到 Tomcat2，而 Tomcat2 上没有该用户的 Session，导致登录校验失败。

5.2 传统方案：Session 拷贝

早期通过 Session 拷贝实现共享：任意一台服务器的 Session 修改时，同步给其他 Tomcat。但存在两个问题：

  1. 每台服务器都保存完整的 Session 数据，服务器压力过大；
  2. Session 拷贝存在延迟，可能导致短时间内数据不一致。

5.3 解决方案：用 Redis 代替 Session

Redis 数据本身是共享存储的，多台 Tomcat 都访问同一个 Redis，天然解决 Session 共享问题。Redis 实现登录的具体代码明日再学。
